Unit 1: Core Financial Accounting (FI) Configuration

Unit objectives: Build the organizational skeleton of FI in SAP ERP (ECC): create a company code and tie it to a company and a controlling area, verify the ledger set-up of New G/L Accounting, understand the variant principle, define fiscal year variants, and grasp how currency keys, exchange rate types and exchange-rate maintenance tools work.

Lesson 1: Managing Organizational Units in Financial Accounting (FI)

Learn what a client, company code and the optional FI organizational units are, how to create a company code by copying, and how to assign it to a company ID and to a controlling area.

The organizational hierarchy

The client is the top node of an SAP ERP system. Technically it is a self-contained unit with its own master data, tables and transaction data; in business terms it corresponds to a corporate group. Anything defined at client level (for example exchange rates) is valid for every organizational unit below it and never has to be repeated. To log on through the SAP GUI a user needs a client key and a user master record inside that client.

The company code is the smallest organizational unit for which a complete, self-contained set of accounts can be kept and for which statutory financial statements (balance sheet and P&L) are produced. It is the only mandatory structure in SAP ERP Financials and the most important FI organizational unit. Because tax authorities in each country want a separate legal entity, an international group normally creates one company code per country. Rule of thumb: every entity that must publish its own balance sheet and P&L gets a company code.

Creating a company code

SAP recommends never building a company code from scratch. Instead use the IMG activity Enterprise Structure → Definition → Financial Accounting → Edit, Copy, Delete, Check Company Code (SPRO, or directly EC01) and the function Copy, delete, check company code. Copying transfers:

  • the definition (basic data),
  • the global parameters,
  • the Customizing tables,
  • the G/L accounts (optional – a dialog asks whether to copy the company-code segment of the G/L accounts; answer yes only if the target should use the same chart of accounts),
  • the account determination.

Afterwards only the deviating settings need to be changed in Edit Company Code Data. The key is a four-character alphanumeric code that has to be entered with every company-code-specific posting or master record.

Country templates

Company code 0001 is delivered as a neutral template using the international chart of accounts INT. If a country template exists, the country installation program copies the country-specific Customizing into company code 0001; you then copy 0001 into your own company code. The same program can also prepare country-specific templates for controlling areas, plants, purchasing and sales organizations, credit control areas and FM areas. Two cautions: never use 0001 productively, because the country installation always overwrites it, and run the program only during an initial installation, never after an upgrade, because the country-specific Customizing structure may change between releases.

Optional organizational units in FI

Everything beyond the company code is optional and chosen according to legal or internal reporting needs. The guiding questions are: for which parts of the business is separate reporting required, and for which areas of responsibility must a separate balance sheet or P&L be produced?

Controlling area assignment

The controlling area is the central organizational unit of Controlling: a closed structure within which costs and revenues are managed and allocated. Several company codes may share one controlling area (cross-company-code controlling) provided they all use the same operating chart of accounts and the same fiscal year variant. Key takeaways
  • Client = corporate group; company code = legal entity with its own statutory financial statements; the company code is the only mandatory FI unit.
  • Create company codes by copying (1010 in the course, 0001 as the delivered template) so that global parameters, Customizing and account determination come along.
  • Profit center, segment, company, functional area and business area are optional and answer specific reporting needs; segments are normally derived from profit centers.
  • Several company codes can share a controlling area only with a common operating chart of accounts and fiscal year variant.

Lesson 2: Checking the Basic Settings in New General Ledger (G/L) Accounting

Understand how New G/L Accounting represents parallel accounting with a leading and non-leading ledgers, how it differs from the accounts approach, and how scenarios decide which fields the ledgers update.

Leading ledger and non-leading ledgers

New G/L Accounting delivers the leading ledger 0L with the totals table FAGLFLEXT. Each client has exactly one leading ledger; since EHP 7 a ledger other than 0L may be declared leading. Every company code is automatically assigned to the leading ledger, it cannot be deactivated, it carries the group valuation view, it is integrated with all subledgers and is updated in all company codes. Asset Accounting depreciation area 01 is always tied to it, and in the standard system only leading-ledger values flow to Controlling.

Non-leading ledgers run in parallel and are activated manually per company code, typically to represent a local accounting principle. They may use their own fiscal year variant and their own second/third parallel currency. Using several ledgers for several GAAPs is the ledger approach.

Accounts approach versus ledger approach

The accounts approach posts the different valuations to different G/L accounts and lets the financial statement version pick the relevant accounts per GAAP. It also works in classic G/L Accounting. SAP regards both approaches as equally valid.

Scenarios

A scenario specifies which fields of the general ledger view are updated when other components post to the ledger. Scenarios are delivered by SAP, cannot be created by customers, and are assigned to ledgers in Customizing (Financial Accounting (New) → Financial Accounting Global Settings (New) → Ledgers → Ledger → Assign Scenarios and Customer Fields to Ledgers). A ledger may carry one, several or all six scenarios; you need a ledger per accounting principle, never a ledger per scenario. Non-leading ledgers are optional, so scenario assignments to them are too.

  • Non-leading ledgers are activated per company code and may have a different fiscal year variant and parallel currencies.
  • Ledger approach and accounts approach are both SAP-recommended ways to handle parallel accounting.
  • Scenarios (six, SAP-delivered) decide which fields a ledger updates; assign the ones you need, not one ledger per scenario.

Lesson 3: Outlining the Variant Principle

Recognize the recurring three-step pattern by which SAP ERP attaches shared properties to many objects.

The principle

Whenever several business objects share the same properties, SAP bundles those properties into a variant so that they are maintained once and reused. The method always has three steps:

  1. Define the variant (give it a key and a description).
  2. Determine the values of the variant (its content).
  3. Assign the variant to the objects that should use it (e.g. company codes).

In FI the principle appears for field status variants, posting period variants and fiscal year variants. Knowing the pattern makes each of those Customizing areas immediately familiar: the same variant can be shared by many company codes, and a change to the variant affects all of them at once.

Key takeaways
  • Variant principle = define, fill with values, assign.
  • It reduces maintenance because one variant serves many objects.
  • Used for field status, posting periods and fiscal years.

Lesson 4: Managing Fiscal Year Variants

Define how a fiscal year is split into posting and special periods, distinguish year-independent from year-specific variants, and assign a variant to a company code.

What the fiscal year variant contains

Business transactions have to be assigned to periods, so the fiscal year is defined as a variant and attached to the company code. A fiscal year variant holds the posting periods and the special periods: at most 16 periods in total, for example 12 posting periods plus 4 special periods (13–16). Special periods are not time intervals; they hold year-end closing postings. The system derives the posting period from the posting date; when the date lies in the last normal period the user may choose one of the special periods instead. Standard variants (e.g. K4) are delivered as templates.

Important limitation: the fiscal year variant says nothing about whether a period is open; that is handled by the posting period variant (Unit 3). It only defines how many periods exist and when they start and end.

Year-independent variants

If every year has the same number of periods with the same start/end days, the variant is year-independent. Two flavours:

TypeDefinitionNotes
Calendar yearPosting periods = calendar monthsMust have exactly 12 posting periods; just tick Calendar yr.
Non-calendar yearPeriods defined by their end dates (month/day)1 to 16 periods. If the year does not start on 1 January, periods belonging to the previous or next fiscal year get a year shift of -1 or +1. If periods are months, use day limit 29 for February to cover leap years.

Example from the course: a fiscal year from April to March with six periods; January–March still belong to the old fiscal year and therefore carry year shift -1.

Year-specific variants

A variant is year-specific when period start/end dates differ between years or when some years have a different number of periods. If all years have the same number of periods, only the period dates per year need to be entered. A year with fewer periods than usual is a shortened fiscal year, needed when closing must happen early (change of fiscal year start, sale of the company). The shortened year and its number of periods must be defined before the period dates; a shortened year can only have fewer periods.

  • … → Assign Company Code to a Fiscal Year Variant (OB37).

Key takeaways
  • Up to 16 periods: posting periods derived from the posting date plus special periods for closing entries.
  • Year-independent = calendar (12 months) or non-calendar (end dates with -1/+1 year shift); year-specific = dates or period count differ between years (shortened fiscal year).
  • The fiscal year variant does not open or close periods.

Lesson 5: Identifying the Basic Functionality of Currency Keys and Exchange Rate Types

Understand how currencies and exchange rate types are defined, how translation ratios and quotation types work, and which tools cut the effort of keeping exchange rates current.

Currency keys and exchange rate types

Every currency is identified by a currency key; SAP delivers the standard ISO keys and each key may carry a validity date. Exchange rate types separate rates by purpose – valuation, conversion, translation, planning. The most common are M (average rate, used for posting and clearing), G (bank buying rate) and B (bank selling rate). Rates are maintained per exchange rate type and currency pair, with a validity date, in table TCURR.

Translation ratios

Before rates can be entered, the translation ratio (e.g. 1:1 or 1:1000) for each exchange rate type and currency pair must be maintained. Normally this is a one-off job, but because inflation can change the relationship, ratios are time-dependent.

Tools that reduce maintenance

ToolHow it works
InversionIf EUR→USD is maintained, USD→EUR is derived automatically. Considered old and rarely used today.
Exchange rate spreadsThe spread between the average rate and the buying/selling rate is usually constant; enter the spread once per exchange rate type and maintain only the average rate; B and G are calculated by adding/subtracting the spread.
Base currencyAssign a base currency to an exchange rate type and maintain only the rates of all currencies against it; a rate between two foreign currencies is derived by chaining two rates.

Only one tool can be used per exchange rate type, but different types may use different tools. The efficient combination recommended by the course: base currency for the average rate type M, spreads for B and G. Rates can also be loaded automatically: report RFTBFF00 imports market data files (MultiCash format), and RFTBDF07 / RFTBDF14 use a datafeed interface with RFC for real-time transfer.

Direct and indirect quotation

With local currency EUR and foreign currency USD:

  • Direct quotation: 1 USD = 1.2663 EUR – the price of one unit of foreign currency in local currency.
  • Indirect quotation: 1 EUR = 0.7897 USD – the price of one unit of local currency in foreign currency.

The quotation setting applies system-wide, not per application or country. Per currency pair you declare one quotation as the standard; a rate entered in the other quotation is highlighted. Prefixes distinguish the two during entry and display:

ScenarioPrefix settingEffect
Mostly direct quotation (standard)blank = direct, "/" = indirectDirect rates can be entered without prefix.
Both quotations commone.g. "*" = direct, "/" = indirectNo rate can be entered without a prefix; users are forced to think about the quotation.
Mostly indirect quotation"*" = direct, blank = indirectIndirect rates without prefix; the rarer direct rates need the prefix.

SAP Note 783877 collects FAQs on currency translation.

Worklists for exchange rate maintenance

When many people maintain TCURR, problems arise: wrong rates, wrong quotation, long scrolling in a huge table, and the table cannot be edited by several users at the same time. Since SAP R/3 Enterprise you can define worklists and maintain them with transaction TCURMNT: each worklist shows only the relevant rates and quotation, can be protected by authorizations, is small and clear, and different worklists can be processed in parallel.

Key takeaways
  • Currencies = currency keys; rates are kept per exchange rate type (M, G, B…) and currency pair with translation ratios.
  • Base currency, exchange rate spreads and inversion each reduce maintenance; one tool per exchange rate type.
  • Direct quotation prices one foreign unit in local currency; indirect prices one local unit in foreign currency; prefixes make the quotation explicit.
  • TCURMNT worklists let several users maintain only their slice of TCURR safely.

Lesson 1: Maintaining General Ledger (G/L) Accounts

Understand how a chart of accounts and its account groups structure G/L master data, how the chart-of-accounts and company-code segments work together, and how to control, create and mass-change G/L accounts, including group and country charts of accounts.

The chart of accounts

A chart of accounts is a variant (define → values → assign) that holds the structure and the basic information of all G/L accounts. It is identified by a four-character key and defined with:

AttributeMeaning
Key and namee.g. INT (international), IKR, CAUS, or a country-specific chart
Maintenance languageLanguage in which account descriptions are maintained; shown when no translation exists in the logon language
Length of G/L account number1 to 10 digits
Controlling integrationWhether/how cost elements are created automatically for P&L accounts (no default = no cost element)
Group chart of accountsConsolidation chart; once assigned, the group account number becomes a required field in every account
Block indicatorBlocks an incomplete chart so that no company code can use it

Every company code must have exactly one chart of accounts assigned, but – variant principle – one chart can serve many company codes. FI and CO share the chart, so company codes that do cross-company-code controlling must use the same operational chart (in the course example CC1000 and CC2000 can, CC2000 and CC3000 cannot). Useful reports: RFSKPL00 (G/L account list of a chart), RFSKVZ00 (account directory with chart and company code data), RFSKTH00 (account assignment manual with the account texts).

Two segments of a G/L account

A G/L account consists of a chart of accounts segment and one company code segment per company code that uses the account. The chart segment is entered once and is valid for every company code; it holds the account number, short and long text, control fields (account group, P&L/balance sheet indicator, P&L statement type), consolidation fields (group account number, trading partner) and texts managed by text ID and language. It can be translated so that the account name appears in the user's logon language. Keywords support searching.

The company code segment adds the data that governs posting and account management in that company code: account currency, tax category, reconciliation account indicator, line item display, sort key, field status group, house bank, interest calculation data. Because the number and name live in the chart segment, an account keeps the same number and name in all company codes, while each company code can set its own control data (e.g. tax category on in one company code and off in another). A company code that does not need an account simply creates no segment for it; another company code in the group may use the same number for, say, a foreign-currency balance sheet account.

The layout of the master-data tab pages (number of tabs, titles, field groups and their position, separate layouts for central, chart-specific and company-code-specific processing) is configurable; SAP delivers layouts that can be copied and assigned to a chart or account group.

Balance sheet versus P&L accounts

The chart segment declares the account type, which decides what happens at balance carryforward:

TypeYear-end behaviour
Balance sheet accountBalance carried forward to the same account.
P&L accountBalance moved to a retained earnings account, account reset to zero. The P&L statement type key (e.g. X) in the chart segment points to the retained earnings account defined in Customizing.

With only one retained earnings account the system fills the key automatically when a P&L account is created; with several, the user must choose one per P&L account.

Account groups

Accounts of the same kind (cash, material, asset, P&L…) are gathered into account groups. The account group is a required field in the chart segment and does two things: it carries a number range so that accounts of one type share a number interval (G/L intervals may overlap), and it controls the field status of the company code segment, i.e. which fields appear when a company code segment is maintained. Example: force line item display to required for the cash-account group so every cash account shows its line items. SAP delivers predefined groups; IMG: Financial Accounting (New) → General Ledger Accounting (New) → Master Data → G/L Accounts → Preparations → Define Account Group (OBD4).

Field status of G/L master data

Each field (or field group, e.g. the three interest-calculation fields) can be Hide (not used), Display (visible but unchangeable), Required or Optional. Account currency and field status group are always required and cannot be changed. Even a hidden field may still hold a value that takes effect.

The field status is normally driven by the account group; a second, transaction-dependent layer (Define Screen Layout for Each Transaction: Create, Change, Display) is used mostly to protect fields after creation – e.g. set the currency of a GBP cash account to Display in the Change transaction. When the two layers disagree the higher priority wins, in the order Hide > Display > Required > Optional. In a Display transaction fields can only be displayed or hidden. Setting a layer to Optional everywhere effectively switches it off, because Optional always loses.

Reconciliation accounts

A reconciliation account is a G/L account that collects the postings of a subledger (customers = receivables, vendors = payables, also assets). Every posting to a subledger account is simultaneously written to its reconciliation account, so the general ledger is always complete and in balance with the subledgers. The account type is set in the field Reconciliation account for account type in the company code segment and the account then serves only that type. Direct postings to a reconciliation account are not possible.

Line item display and open item management

Transaction figures are the debit and credit totals of an account; the balance is their difference. The Line item display flag (company code segment) decides whether only totals are updated (user sees the balance only) or whether the key data of each line item is additionally written to an index table so items can be listed online. Because this costs storage and time, use it only where no other view of the items exists; report RFSEPA01 activates it retroactively. In New G/L this flag only concerns the entry view; in the general ledger view line items of all accounts are always visible, because the subledger alone cannot explain the ledger (e.g. profit center and segment created by document splitting exist only there).

Open item management makes every item either open or cleared, which is the prerequisite for checking that a transaction has an offsetting entry; open and cleared items can be listed separately. It requires line item display, can be switched on or off only when the balance is zero, and is typical for bank clearing, GR/IR clearing and salary clearing accounts. If OI management is set up per ledger, ledger-group-specific clearing is available.

Ways to create and change G/L accounts

  • One-step (centrally): chart and company code segment together – FS00.
  • Two-step: chart segment first (FSP0), company code segment afterwards (FSS0).
  • Copy: create with reference to another account; copy a whole company code segment to another company code; copy an entire chart of accounts including account determination; copy the financial statement version.
  • Data transfer: program RFBISA00 and batch input interfaces, adapted by the ABAP team, for migrating charts of accounts.
  • Collective processing (OB_GLACC11/12/13): change chart data, company code data or descriptions of many accounts at once, even across charts, by selecting the fields and entering a new value that replaces the old one. Check carefully – changes take effect on saving and can have wide consequences.

Lesson 2: Creating Profit Centers and Segments

Learn what the segment characteristic is for, how it is derived from the profit center, what to do when derivation is impossible, and how segments can be reorganized.

The segment characteristic

The segment is a standard FI account assignment object below the company code, designed to analyse business activity areas such as markets or products and to satisfy the segment reporting rules of IFRS 8 and US GAAP. Business area and profit center could also be used, but both were historically used for other purposes, so SAP added the segment as a clean object. IFRS 8 describes a business segment as a part of the company that earns revenues and incurs expenses (including internal ones), whose results are regularly reviewed by the chief decision-maker for resource allocation, and for which separate financial information exists.

Deriving the segment

The standard derivation is to store a segment in the profit center master record: every posting to the profit center then automatically carries the segment; a profit center without a segment produces no segment posting. SAP Note 1035140 states the rules: segments are officially supported only together with profit centers; automatic derivation works only via profit centers; in many logistics transactions a segment cannot be entered manually; and various standard interfaces ignore segments. When derivation from the profit center is not possible, New G/L with document splitting offers manual entry, the BAdI FAGL_DERIVE_SEGMENT, substitution rules, or assignment via standard accounts. Profit Center Accounting originated in CO but, because of its importance for external reporting, now lives in FI (New G/L); management must decide whether it serves internal or external accounting.

Reorganizing segments

Changing the segment of profit centers (e.g. moving profit centers 1 and 3 to a new segment SEGA) touches far more than the profit center master: G/L totals of open-item-managed accounts, receivables, payables and asset reconciliation totals, asset master records and allocation cycles all carry the old segment. The Reorganization of Segments function supports and executes such re-assignments, including merging segments, with two roles: the reorganization manager (chief accountant/central controller) who owns the plan, and the object list owners (FI/CO accountants) who process their objects.

Lesson 1: Configuring the Header and Line Items of Financial Accounting (FI) Documents

Learn the document principle, the two control keys of an FI document (document type for the header, posting key for the line items), document number ranges, and how field status groups and variants decide which fields appear during document entry.

The document principle

SAP ERP posts every business transaction as a document that stays in the system as a complete unit until it is archived. A document is uniquely identified by document number + company code + fiscal year. It consists of a header (data valid for the whole document, e.g. dates, document type, currency, reference, header text) and 2 to 999 line items. Logistics components post through the AC interface, which creates accounting line items that are nearly identical in most fields; SAP Note 36353 explains how to summarize such documents.

One business transaction may create several documents: a goods receipt produces a material document (inventory data) and an accounting document (accounts and amounts). Other transactions, such as a purchase order, create no accounting document at all because they do not touch accounting. Related documents are linked so that the whole business process can be traced. Reports: RFBELJ00 compact document journal (key header and item data of selected documents); RFBUEB00 / RFBUEB01 to locate documents; RFBNUM00 to find gaps in document numbering.

Document types

The document type classifies business transactions and controls the header. It is defined at client level, so it applies to all company codes; SAP delivers types that can be copied or changed. Lesson 2: Managing Posting Periods

Learn how the posting period variant opens and closes periods per account type and account interval, how the two (three) period intervals and authorization groups work, and how the system derives the period from the posting date.

Open and closed periods

The fiscal year variant defines the periods; the posting period variant decides which of them are currently open. Normally only the current period is open and all others are closed; at period end the old period is closed and the next one opened by adjusting the ranges. Any number of periods may be open, and during year-end closing the special periods are opened for closing entries. Following the variant principle, one posting period variant can be assigned to many company codes, which are then opened and closed together.

IMG: Financial Accounting (New) → Financial Accounting Global Settings (New) → Ledgers → Fiscal Year and Posting Periods → Posting Periods → Define Variants for Open Posting Periods (OBBO), Open and Close Posting Periods (OB52), Assign Variants to Company Code (OBBP).

The account interval (from/to account) always refers to G/L accounts; for subledger types you enter reconciliation accounts, so customers or vendors with a particular reconciliation account can be treated differently from the rest.

During closing two periods must be open simultaneously, therefore each line has two period intervals. Interval 1 can be protected by an authorization group: only users holding authorization object F_BKPF_BUP with that group value may post in it. At entry the user types the posting date; the system derives posting period and fiscal year from it using the fiscal year variant, checks the posting period variant, and updates the transaction figures of that period. The account balance display shows the figures per period.

Lesson 1: Analyzing Document Splitting

Understand the entry view and general ledger view of a New G/L document, how document splitting produces zero balances for profit center or segment, the passive/active/zero-balance steps, and the Customizing behind it.

Two views of a document

In New G/L every FI document has a data entry view (how the creator entered it and how it appears in the subledgers) and a general ledger view (how it is stored in the leading and non-leading ledgers). Both views always exist; this cannot be switched off. Classic G/L has only one view, which corresponds to the entry view. Without document splitting both views are identical.

What document splitting does

Document splitting (also called online split) distributes line items that carry no reporting characteristic – typically the vendor/customer line and the tax line – according to the lines that do carry one (the expense or revenue lines), so that every characteristic such as profit center, segment or business area balances to zero within the document. This is what makes a complete balance sheet below company code level possible. In the course figure a vendor invoice with two expense lines (accounts 477000 and 417000, different profit centers/segments) is shown: in the general ledger view the vendor and tax lines are split proportionally to the two expense lines. The split is visible only in the general ledger view; the entry view still shows the original unsplit lines. Document splitting is only for companies that need (or want) an additional reporting dimension on the balance sheet.

Lesson 3: Configuring Change Control

Learn which fields of a posted document may still be changed, how document change rules are defined, and how changes are logged and reported.

What can be changed

A posted document can be changed (FB02), but only in fields that do not affect the accounting substance. Changeable by default: in the header the reference and header text; in the line items the assignment, text and payment terms (and other payment-related fields such as payment block or dunning data). Amount, posting key, account and anything else that influences reconciliation can never be changed – that requires a reversal. Every change is logged with field, old and new value, user, date and time; report RFBABL00 lists document changes, selectable by company code, document number, fiscal year, change date and user.

Reversal basics

Errors are corrected by reversing the wrong document and posting it again correctly; this keeps a full audit trail. A reversal reason must always be entered; the reason also controls whether the reversal date may differ from the original posting date (otherwise the original posting date is used). A document containing cleared items cannot be reversed until the clearing is reset (FBRA). The document type used for the reversal comes from the reverse document type of the original document type.

Lesson 6: Maintaining Taxes and Tax Codes

Learn which tax systems SAP ERP supports, how the tax calculation procedure, tax codes, rates and account keys work together, and how tax accounts and tax categories on G/L accounts are set up.

Tax systems and types

SAP ERP handles taxes on sales and purchases (VAT), US sales and use tax, country-specific additional taxes (investment tax in Norway, clearing tax in Belgium) and withholding tax. Rates may be defined nationally (uniform) or at state/jurisdiction level; the US has more than 67,000 jurisdictions, so external tax software is often connected through SAP's generic interface. Some countries (Canada, India, Brazil) tax on both levels. The system checks or calculates the tax amount, posts it to tax accounts, and adjusts tax for cash discounts and other deductions. The tax base is the expense/revenue amount, taken gross (including cash discount) or net (after cash discount) as national law requires, set per company code or top jurisdiction level.

Tax calculation procedure

Every country has a preconfigured tax calculation procedure (e.g. TAXD, TAXUSJ with jurisdiction codes, TAXUSX for an external tax package) assigned to the country. It consists of:

  • a sequence of steps, each with a from step telling where its base value comes from;
  • tax types (condition types, e.g. MWS output tax, VST input tax) valid for the country; the condition type decides whether the base is "percentage included" or "percentage separate";
  • account keys (transaction keys, e.g. MWS, VST, NVV) used for automatic account determination – use the delivered keys.

Tax codes and rates

The tax code entered in the document links the item to the calculation procedure. It belongs to a country key, or to country + jurisdiction code in jurisdiction-based countries, where codes are also date-dependent (document or posting date can be chosen as the valid date). IMG: Financial Accounting Global Settings (New) → Tax on Sales/Purchases → Calculation → Define Tax Codes for Sales and Purchases (FTXP): properties (name, tax type A output / V input, check indicator), the rate per tax type, and the tax accounts per chart of accounts. Usually one rate is entered; several rates appear for example when 10 % input tax is 40 % non-deductible – 6 % deductible input tax plus 4 % non-deductible. Zero-rate codes are needed for tax-exempt items that must still be reported and for tax-exempt transactions such as goods issues. The check indicator turns a deviation between calculated and entered tax into an error instead of a warning; it is not set for input tax codes because the amount from the vendor's invoice must be posted as printed.

Tax postings and account determination

Normally the calculated tax is posted as a separate line to a tax account. For certain account keys (e.g. NVV, non-deductible input tax or sales tax payables) the tax is distributed onto the expense or revenue lines instead. Automatic account determination (Posting → Define Tax Accounts, OB40) assigns to each account key the tax account(s), the posting keys (40/50 recommended) and the rules (whether determination depends on tax code and/or account key). Exchange rate differences from tax adjustments in foreign currency normally go to the regular exchange rate difference account; per company code you can instead let the tax exchange rate be entered manually or taken from posting/document date and post the resulting difference to a special account.

Concept

Cross-company code transactions occur with central procurement (one company code buys for others), central payment (one pays for others) or intercompany sales. Since a document belongs to exactly one company code, the system creates one document per company code and inserts automatically generated lines on clearing accounts (receivable/payable between the companies) so that each document balances. All documents share a cross-company code transaction number built from the first document number + first company code + fiscal year, stored in every header for the audit trail. Clearing accounts

IMG: General Ledger Accounting (New) → Business Transactions → Prepare Cross-Company Code Transactions (OBYA). For each pair of company codes you define the clearing account and posting key for receivables (debit) and payables (credit) in both directions; the clearing account can be a G/L account, a customer or a vendor account (the posting key identifies the type). Every possible pair needs an entry: three company codes need 3 × 2 = 6 assignments; with a designated clearing company code only 2 × 2 = 4 are needed.

Lesson 1: Performing Open Item Clearing

Understand the two clearing transactions (account clearing and post with clearing), the automatic clearing program, the assignment field as sort criterion, the manual payment screen, automatic clearing postings and the reset of clearing.

Open items and clearing

An open item is an incomplete business transaction, e.g. an unpaid invoice. A transaction is complete when a clearing posting brings a group of items to a zero balance; the items then carry the clearing document number and clearing date (today or a user-defined date). Documents with open items cannot be archived. Clearing always produces a clearing document. Typical flow: invoice posted (open) → customer pays and the payment is assigned to the invoice → both items cleared. Manual clearing is common for bank sub-accounts and clearing accounts, debit memo procedures, and vendor refunds.

Automatic clearing program

The clearing program (F.13 / F13E, SAPF124) clears G/L and subledger accounts automatically. It groups items of an account that agree in company code, account type, account number, reconciliation account, currency and special G/L indicator, plus up to five user-defined criteria from header or item (e.g. assignment, reference) configured per account type and account range in Prepare Automatic Clearing (OB74). Groups whose local-currency balance is zero are cleared with a clearing document. Not cleared: noted items, statistical postings and some bill-of-exchange special G/L transactions, down payments (unless matching down payment clearing items exist), and items with withholding tax.

The assignment field

The assignment (BSEG-ZUONR) is filled automatically according to the sort key in the master record (company code segment of the G/L account or business partner). It can combine up to four fields with a total of 18 characters, e.g. document number (10) + posting date (6). Sort key = purchase order number fills the partner item with the PO number; sort key = cost center fills G/L items with the cost center. Line item display and clearing sort by this field, which is why the clearing program often groups on it. For SD billing, reference and assignment of the billing document (configurable: PO, order, delivery or billing number) are copied into the FI document, so the originating sales document can be traced and used as selection criterion.

Lesson 3: Managing Exchange Rate Differences

Understand how realized exchange rate differences arise when foreign-currency open items are cleared, how they interact with valuation at period end, and how gain/loss accounts are determined.

Realized differences at clearing

When an open item in foreign currency is cleared at a different rate than it was posted, the local-currency amounts differ. The system posts this realized exchange rate difference automatically to a gain (revenue) or loss (expense) account defined in Customizing and stores the realized difference in the cleared line item. If the item had already been valuated for the financial statements (foreign currency valuation at period end posts the unrealized gain/loss to a balance sheet adjustment account and an expense/revenue account), the clearing first reverses the adjustment-account posting and then posts the remaining difference as realized gain or loss.

Account determination

Every reconciliation account and every G/L account with open items in foreign currency must have gain and loss accounts assigned for realized differences (General Ledger Accounting (New) → Periodic Processing → Valuate → Foreign Currency Valuation → Prepare Automatic Postings for Foreign Currency Valuation, OBA1, transaction KDF). The granularity of the assignment can be:

LevelExample
One set of accounts for all currencies and currency typesSingle gain and loss account per G/L account
Per currency and currency typeSeparate accounts for USD/10, USD/30…
Per currencySeparate accounts for USD, GBP…
Per currency typeSeparate accounts for company code currency vs. group currency

In the same place the accounts for unrealized valuation differences (balance sheet adjustment account, valuation gain/loss) are maintained, which is why the clearing can reverse the valuation correctly.

Key takeaways
  • Clearing a foreign-currency item at a changed rate creates a realized exchange rate difference, posted automatically to gain/loss accounts and stored in the cleared item.
  • Previously valuated items: the balance sheet adjustment is reversed first, then the remaining difference is realized.
  • Gain/loss accounts are mandatory for all reconciliation and open-item G/L accounts with foreign currency items and can be differentiated by currency and/or currency type.

It contains the new HANA-based SAP Accounting and Cash Management and tighter integration between ERP and BPC (Business Planning and Consolidation).

Problem with the classic architecture: FI line items (BSEG) and CO line items (COEP) were linked only at header level. Consequences: heavy reconciliation when granularity differs (e.g. payroll posts more FI than CO items), difficult reporting between FI and CO-PA, and no single report combining the legal view with responsibility or market-segment detail.

New architecture: the account becomes the leading dimension for both FI and CO views; FI dimensions (company code, business area, segment, profit center…) and CO dimensions (cost center, order, WBS element, product, customer, region…) are stored together on one combined line item. Results:

  • Reduced reconciliation between FI and CO.
  • A one-document view through the logical link of BSEG and COEP; drill-down from an aggregated P&L to line items by customer, product or region; detailed queries over all spend categories; journal entries linked to their source documents (sales order, material movement…); selection from roughly 400 fields thanks to HANA speed.
  • Modern UIs, cockpits and embedded BI; harmonized internal and external accounting; faster closing and reporting; lower total cost of finance.

Note the ECC-to-S/4 lineage: Simple Finance 1.0 introduced the universal-journal idea (no totals tables, FI and CO converged) that later became ACDOCA in S/4HANA Finance.

Key statements from the course: the migration to the G/L in SAP Accounting is short and can be done at any period end; a migration guide and monitor are provided and no SAP migration service is mandatory; changes to coding block, interfaces, security and reporting are optional; New G/L is not a prerequisite – classic G/L customers can migrate directly, their data is transferred automatically into the new structures, and EC-PCA and FI-SL may remain in place; the G/L in SAP Accounting offers the same capabilities as New G/L, reuses its data structures, and is optimized for HANA (better reporting, convergence with CO, no totals tables). Customers already running a New G/L migration project with a 2015 go-live should finish it first. The one hard prerequisite is that the ERP system already runs on the HANA database. Useful references: SAP Note 1976487 (adjusting customer programs to the simplified data model), help.sap.com/sfin100, the Administrator's Guide for Simple Finance Add-On 1.0.

Key takeaways
  • HANA = one in-memory copy of data for OLTP and OLAP; logic is pushed down to the database.
  • Financials gain a single source of truth at line item level with all dimensions, on-the-fly closing and reporting.
  • Simple Finance merges FI (BSEG) and CO (COEP) views on one line item with the account as leading dimension, removing FI/CO reconciliation.
  • Migration works from classic or New G/L (New G/L is not required); the system must already be Suite on HANA; totals tables disappear.
